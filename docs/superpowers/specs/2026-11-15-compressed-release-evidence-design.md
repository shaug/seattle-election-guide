# Compressed durable release evidence design

Scope: #762. This document defines the staged format migration and its required acceptance; original task records are retained separately.

## Intent and boundaries

Ordinary releases currently write publication, upload-recorded and verified checkpoints as v1 report/index/seal groups: General128 used 3 + 3 + 9 comments. Preserve those three recovery boundaries and every original receipt/report byte, while making each common-case checkpoint one atomic comment. Preserve all existing bot ownership, producer/source, publication/upload, strict production verification, historical Primary and Updates contracts. No UI, election-data, permission-map, credential, actor or producer-identity change. Do not edit or delete an existing comment. Keep #761 and its source/branch ownership separate. Heavy work and publication remain serial; SB and Currents have priority.

## Selected approach and alternatives

The selected approach is deterministic gzip/base64 in a self-contained v2 issue-comment envelope, with bounded multipart fallback. A readable release/state/run link precedes collapsed encoded content. Uncompressed v1 chunking cannot meet the requested ordinary three-comment outcome; Actions-only storage cannot preserve durable recovery after expiry. Both are excluded by the approved requirements. Existing v1 readers/writers remain supported; this is a format migration, not a new evidence store.

## Codec and limits (implementation choices)

A canonical JSON envelope has schema_version 2.0 and files keyed by validated report name. Each file carries its original UTF-8 text and SHA-256, including receipt.json. Original report bytes must already be canonical UTF-8 JSON under the existing contract. Gzip uses mtime=0. The marker binds exact producer, release, phase/state, canonical operation digest, gzip+base64 format, and compressed/uncompressed sizes and hashes. Authenticate the fixed GitHub Actions bot before accepting owned machine evidence; then validate every marker, byte hash and the ordinary typed receipt/report contracts.

Keep the existing strict body bound: fewer than 60,000 characters. Limit reports to 16, each original report to 8 MiB, the complete decoded envelope to 16 MiB, and compressed content to 4 MiB. These new ceilings bound the existing UTF-8 JSON report contract, retain the actual 141,815-byte General128 wait report and existing large Unicode/report cases, and leave ample room for full repeated strict reports. Limits are explicit rejection boundaries, never truncation. Multipart gzip chunks are at most 32,768 bytes, at most 128 parts; the final seal carries immutable IDs, order and SHA-256 for every part and remains within the same comment bound. No recursive unbounded index is needed.

Decode base64 strictly; bound encoded input before allocation, decompress with a bounded output budget, require exactly one complete gzip member and reject trailing/unused/unconsumed data. Reject duplicate JSON keys, invalid names, unknown fields, wrong lengths/hashes, excess report/part counts, duplicate IDs and mixed identities. Reconstruct and hash the original report bytes after decompression. Do not infer successful upload/verification from a seal alone.

## Dual reader integration

Keep PartMarker and all v1 bytes unchanged. Add a distinct typed v2 marker and retain actual comment IDs; do not manufacture v1 IDs in production reads. The existing _comments/_completed boundary combines both representations and applies the same publication, canonical-upload and strict-report validation. Exactly identical operations represented in both formats are one completed operation only when every report byte agrees; conflicting representations fail closed. Complete receipt fragments still constrain canonical upload identity. Any unsealed v2 group remains pending and blocks pre-upload disposition, like incomplete v1 evidence. Current consumers keep their public interfaces.

## Writer and uncertain outcomes

Stage A leaves retain_evidence's active default at v1. A reusable v2 codec/reader can be tested without activating production v2 writes. Stage B selects v1 whenever the exact operation already has any v1 parts, continuing those immutable IDs; a matching completed v2 operation is reused. Otherwise write one envelope, or missing multipart chunks followed by a seal. Compare all pre-existing records against the expected complete payload before posting anything. A POST error or ambiguous reply triggers a complete reread before any later retry. Reuse an exact matching posted record; absent or conflicting outcomes remain nonzero and visible. Never blindly re-POST. Preserve the recorded-upload checkpoint before probes and existing local failure artifacts, workflow summaries and failed deployment status semantics.

## Historical execution and rollout ordering

Current ci.yml executes inputs.source_sha, including its old reader code. Current verify-release.yml checks out github.sha and binds the original source separately. Shipping dual readers alone therefore does not upgrade old source. Use the existing current-main verification workflow as the supported compatibility-preparation boundary, with its existing permissions and concurrency unchanged. Add an explicit preparation mode that materializes lossless v1 compatibility records from authenticated complete v2 operations before any historical-source CI is requested. It must preserve original receipt/report bytes, operation digest and producer, use real newly returned immutable comment IDs, resume incomplete v1 groups, and skip matching completed v1 groups. It records the distinct exporter/reader workflow identity and original operation identity in its output; it creates no upload, deployment or invented verification. Conversion is serialization of an existing operation, never a new operation attributed to its original producer.

Preparation must account for the old consumer's global managed-intent checks, not merely its requested source or latest release. Discover every owning issue from the authenticated managed deployment payloads, not merely the requested issue, then validate the relevant complete evidence before any compatibility write. Bound new comments per preparation invocation and report incomplete/conflicting outcomes visibly. No old historical commit is edited, no producer field relabeled, no new permission added. Older direct CI remains guarded; the documented preparation sequence supplies records it can actually read.
