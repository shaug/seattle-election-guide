# Contributing

Work is organized through GitHub issues and focused pull requests. Do not commit directly to
`main`.

## Local checks

```bash
make sync
make check
```

`make sync` installs both toolchains from their lockfiles (`uv sync --frozen`
and `npm ci`). Node is not optional: rendering bundles each page's client entry
module with the pinned esbuild, so `pytest` and `election-guide release build`
both need `node_modules` present (docs/FRONTEND.md, Modules).

`make check` ends in `make check-js`, which lints and format-checks the client
modules with Biome, type-checks them with `tsc --noEmit --checkJs`, and then
runs the Node tests. `make format` fixes both languages: ruff for Python,
`biome check --write` for JavaScript.

The complete pytest suite remains available through `make test`. `make test-unit`
runs isolated component logic with small local fixtures; real sockets, DNS,
child processes and forks are rejected before they run, including when those
units run inside the complete gate. `make test-contract` checks committed data,
repository surfaces and declarations. `make test-integration` exercises actual
Git, artifacts, storage and application flows; `make test-e2e` exercises browser
and whole-page behavior.

`tests/suites.json` owns semantic membership and the required CI partition for
every case, with explicit exceptions for mixed modules. Collection rejects an
unclassified module, a missing partition or duplicate node IDs. CI retains its
four established pytest check names for exact-source promotion and divides the
non-unit work by measured duration across the three integration-named partitions.
Those stable partition names are execution groups, separate from semantic test
kinds. The Make targets and CI use the same collection policy; the coverage
contract requires every collected node exactly once across their union (#651).
Every pytest collection also checks the CI matrix contains each required
partition once, so omitting the lane that holds the coverage test fails before
any remaining lane can execute.

Neither focused target replaces `make check` before proposing a diff.

After staging election-page changes, run `make check-updates` with an authenticated GitHub CLI.
This live comparison is separate from offline `make check`; required CI runs it and production
repeats it before upload. Add a new entry to each affected election's served Updates page in the
same PR. See [RELEASE.md](docs/RELEASE.md#public-update-log) for the exact comparison contract and
an offline diagnostic against a retained production artifact.

`make types` regenerates the client payload declarations from the Pydantic
models (docs/FRONTEND.md, The data contract). Run it after changing anything
the payload publishes and commit the result; `make check` fails while the
committed declarations and the models disagree.

### One gate `make check` does not run

CI builds the general release twice and checks that both builds are the same
release. `make check` does not, and cannot: `election-guide release build`
refuses a dirty checkout, so on the tree you actually run `make check` against
it would fail for a reason unrelated to your diff. Run it yourself, on a clean
tree, before pushing anything that touches rendering, templates, CSS, the client
modules, or the release builder:

```bash
make check-release-reproducible
```

It commits nothing and takes about half a minute. Nothing else here needs it —
a docs-only change cannot move the release build.

**When CI fails this gate.** `release compare` names the deterministic artifact
whose bytes differ between the two builds. Schema 1.2 excludes only the desktop
and mobile rasterized screenshots from that cross-build comparison; they remain
inside the release ZIP for inspection and under the published whole-bundle hash.
A failure therefore means a hashed part of the pipeline is not a pure function
of its inputs — for example, an unordered iteration, clock read, or filesystem
order. It reproduces locally with the command above, which is the same target CI
runs.

It is not a flake to re-run past. If a re-run goes green without a change,
say so on the pull request rather than merging on the second attempt.

## Pull requests

- Link the issue that defines the scope.
- Keep collection, normalization, scoring, and rendering concerns separable.
- Add fixture-based tests for every source adapter.
- Never make ordinary tests depend on live websites.
- Document new policy or methodology choices before using them to score real data.
- State exactly what was verified and what remains incomplete.

Write commit subjects in the conventional form (`feat:`, `fix:`, `docs:`, `build:`) — they become the
text of the software-history entry. New release bundles include software history in their
`RELEASE_NOTES.md`, generated by the pinned local [git-cliff](https://git-cliff.org) from the
reviewed previous-release SHA through the exact source SHA, using the declared version and
source commit timestamp. Creating a tag does not change those notes.

`CHANGELOG.md` is a generated index linking to published releases and retaining historical
sections through `2026-general.10` at the fixed `release_history.legacy_history_end_sha` in
`cliff.toml`. `npm run changelog` regenerates it; `make check` compares committed bytes and tests
tag independence. Do not edit it by hand or append later release sections. Publishing a new
release requires no post-tag changelog PR or second production commit. The automatic publication
path will publish and stage the same merged source revision; historical two-revision lineage
verification remains available for existing releases.

Release operators must follow the executable sequence in [RELEASE.md](docs/RELEASE.md) and the
read-only production probe in [HOSTING.md](docs/HOSTING.md). Preserve the named full candidate SHAs,
release digest, CI artifact, deployment ID, lineage report, and probe output; a branch name or newer
`main` head is not a substitute for an expired exact-candidate artifact.

## Adding sources

Register the organization and its eligibility before collecting results. Record discovery status
even when no current endorsement is found. A new adapter must preserve captures, produce
evidence-linked claims, and include stable local fixtures.

## Adding elections

Create a new election configuration and authoritative race inventory. Do not copy candidates or
races forward from a prior election without current official evidence.

Before merging a release PR, inspect its `candidate-review-<run>-<attempt>` notes,
validation reports, and desktop/mobile screenshots. Prepare its reviewed request with
`election-guide release automation prepare --issue <owning-issue>`, commit it with the
change, and let CI validate the exact PR base. A merge requests automatic archive
publication and production promotion at that same merged SHA. There is no post-merge
screenshot attestation or Publish approval. Documentation/test-only changes run CI
without publishing or deploying another release. See the executable recovery commands
in [RELEASE.md](docs/RELEASE.md); never use a direct local production upload.
